# Tests, the parity harness and the CI gates

The full list of unit suites and Playwright specs is in `docs/claude/test-inventory.md`; add a line there when you add a suite. Four unit suites are GATES that fail on drift: `theme-tokens`, `layout-variants`, `section-fields` and `studio-guide-names`.

- `npm run parity list | capture | compare [page]` runs `scripts/page-parity.mjs`, the rendered-HTML parity harness. It never builds: build first, then capture or compare. Routes are auto-discovered from the build output and baselines live in `scripts/.parity/` (committed, 176 pages (recaptured 2026-10-03; 9 older styleguide__* files sit unused), generated blog archive pages excluded). Use it on any change that is meant to be render-neutral. See PORTS.md card 3. **`npm run parity:capture` / `npm run parity:compare`** bake in `--exclude "blog/page/**,blog/tag/**,blog/category/**/page/**"`, the exclusion this repo's baseline set was recaptured with on 2026-09-20 (plan 2c task 7): pagination, tag and per-category-page archive routes are hundreds of near-identical copies of the same template, so excluding them keeps a real diff from hiding in the noise while the first page of each template still covers it. `npm run parity compare` is 176/176 PASS, and it stays that way across a rebuild. **The one thing to know before you touch this harness is the loop that used to break it:** `scripts/.parity/*.html` is COMMITTED, Tailwind v4 scans every tracked file for classes, and task 7 moved the stylesheet inline, so a capture fed the next build's stylesheet and every page then reported a diff. `src/styles/globals.css` cuts it with `@source not` for `scripts/.parity`, `docs/` and the root Markdown (prose that names a utility class used to keep that class alive too). So a recapture now reaches a fixpoint: capture, rebuild, compare, and the stylesheet's byte count is identical on both sides. **Prove that pair of numbers rather than trusting one green run** -- green for the wrong reason is still red, and `docs/PENDING.md` known gap 2 names the two classes that proved it.
- `npm run check` is the fast gate: `astro check && npm run lint`. `npm run check:full` is `typegen`, build (which includes the embedded Studio) and the unit tests. Together with `npm run format:check`, `npm run check:links` and `npm test` (Playwright), that is what CI runs on every push and PR. `ci.yml` is parallel since PORTS.md card 70: `static` (checks and unit tests), `site` (one build, the link check, the `dist/client` artifact) and `e2e` (Playwright, 3 shards serving that artifact via `PLAYWRIGHT_SKIP_BUILD=1`), with `build` and `test` as aggregator jobs that keep the required-check names. **The fixture env vars in `playwright.config.ts`'s `webServer.env` are duplicated on the `site` build step in `ci.yml`**: the shards no longer build, so a fixture added to one place and not the other makes CI assert against live YouTube, Church Trac or calendar data. `lighthouse.yml` runs `npx lhci autorun` separately, path-filtered, on a one-URL-per-template sample on a PR; `visual.yml` is path-filtered on PR and push. The family test standard is PORTS.md card 35. Run `npm run parity compare` alongside on any change meant to be render-neutral; parity is deliberately a local gate (see the note in `.github/workflows/ci.yml`).
- **Tests must not assert church-authored copy (2026-10-05).** The secretary edits the live site in Sanity whenever he likes, CI builds from LIVE content, and a required spec that named his words went red on every open PR each time he did (two failures in `tests/visit.spec.ts` in one day: a removed band, then renamed subheadings). A failing e2e does not block his publishing (`deploy.yml` runs no Playwright), but it blocks every PR merge and mails failures. So: **a church content edit must never turn `build` or `test` red.** How to write a spec that obeys that:
  - **Assert structure, not words.** Good: a main landmark, headings in order, no overflow at 320, every anchor that exists lands below the header, every link has an `href`, a frame has a title, counts are `>= 1` rather than exact, a `FAQPage` matches the questions shown whichever they are. Not good: a heading's text, a band's name, the exact list of h3s, an FAQ answer sentence, "exactly five accounts", a post named by its slug, an id derived from a heading or a person (`#kendall-ellis`), a taxonomy term (`/blog/tag/advent`), a code typed into Site settings (`8PG6ZJ`).
  - **Ask the build what exists, then test what is there.** `tests/content-helpers.ts`: `findPost` / `postCandidates` (the newest sermon previews, read from the served archive, optionally the first that has what the test needs), `searchWordFromBlog` (a word the newest post certainly contains), `reachableAnchors` / `spread` (the anchor targets on a page, `scroll-mt-*` elements below the first screen). `tests/routes.ts` picks `BLOG_CATEGORY` and `BLOG_TAG` from `dist/client`. Read the church's value out of the page (the install code from the "Get the app" link, the door names from `[data-door-name]`, the contents bar's own ids) and assert the page agrees with ITSELF.
  - **When the subject can vanish, skip with a reason and say where the loss is reported.** `test.skip(n === 0, '... (the @content watch reports it)')`. A structural test that skips silently would be a hole, so every such skip has a matching `@content` test.
  - **Component behaviour belongs on the styleguide.** `/styleguide` and `/styleguide/*` render fixed data and the committed `tests/fixtures/*` (the build's `webServer.env`), so they never move. If a spec is really about how a component renders, point it there instead of at a live page.
  - **What the church is supposed to have said goes in `tests/content-watch.spec.ts`**, with `@content` in the title (`test.describe('@content ...')`). `playwright.config.ts` has `grepInvert: /@content/`, so the required `e2e` shards never run it; `playwright.content.config.ts` (`npm run test:content`, chromium only, no retry) runs ONLY it, from `.github/workflows/content-watch.yml`: daily, after every `Deploy` run (a Sanity publish deploys) and on demand. It is NOT a required check and never runs on a PR; the test step is `continue-on-error`, so drift leaves the run green with a warning annotation and a job summary (`scripts/content-watch-summary.mjs`) rather than a failure email. A drifted expectation means "the content moved": tell the church or update the expectation, do not revert his edit. Keep the dedicated file out of `webkit-iphone`'s `testMatch`.
  - **Do not delete coverage silently.** When a test is removed or loosened, say in the PR what it protected and where that protection lives now. Residual risk on purpose: `a11y`, `contrast`, `reflow` and `headings` still run axe and layout checks over live pages (they are PORTABLE and structural); they can fail only if an edit produces a real accessibility or layout defect (a missing alt, a very long unbreakable word).
